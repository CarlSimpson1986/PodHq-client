## Native FCM push — built, root-caused twice more, and verified live end-to-end — 2026-09-09

**Real bug, found from Carl testing in-app push in the internal test build and getting nothing.** Root cause: the native Android app runs via Capacitor's `server.url` mode, i.e. `myfitpod.app` loaded inside Android's plain system WebView (`BridgeActivity`), not Chrome. `subscribeToPush()`/`send.ts`'s existing implementation is plain browser Web Push (service worker + `PushManager` + VAPID) — fine for real browser/PWA visitors, but a WebView has no persistent background registration to wake the app process on an incoming push the way Chrome does. This was already flagged as an open, untested risk in the 2026-09-07 pre-launch audit; this session is where it actually got hit.

**Fix: added a real native FCM path alongside the existing web-push path, not a replacement.** New `push_device_tokens` table (podHq migration `0095`, separate from `push_subscriptions` since the two delivery mechanisms need different data shapes — endpoint/p256dh/auth vs. a single FCM token). Client: `native-subscribe.ts` (`isNativePushSupported()` gates on `Capacitor.isNativePlatform() && getPlatform() === "android"`, same pattern as `health-connect-client.ts`) uses `@capacitor/push-notifications` to request permission and register a device token, POSTed to new `/api/push/register-device`. `bookings-view.tsx`'s existing enable-notifications UI/auto-resubscribe effect now branches on `isNativePushSupported()` — native permission tracked via `PushNotifications.checkPermissions()` (the WebView's own `Notification.permission` isn't reliable here, so it's not reused for this branch) rather than folded into the existing web `notifPermission` state. Server: `send.ts` now sends to both `push_subscriptions` (web-push) and `push_device_tokens` (Firebase Admin SDK) in parallel per member, combining results; a member can hold rows in both without either impacting the other.

**Gradle wiring**: `@capacitor/push-notifications` installed, `npx cap sync android` run to register it as a native module. The Google services Gradle plugin classpath and its conditional `apply plugin` (gated on `google-services.json` existing) were already present in `android/build.gradle`/`android/app/build.gradle` from the Capacitor Android template — no manual plugin-block edits needed, and Carl was warned off following Firebase's generic "Add Firebase to your app" docs literally, since that would have double-applied the plugin and broken the build. `@capacitor/push-notifications` itself already depends on `com.google.firebase:firebase-messaging` — no separate `firebase-bom`/`firebase-analytics` needed.

**Two real external setup steps, done by Carl this session**: a Firebase project (`my-fit-pod`) created, Android app registered under `uk.co.myfitpod.app`, `google-services.json` downloaded and placed at `android/app/google-services.json` (gitignored — added to `.gitignore` this session, wasn't already). A service-account key generated from the same project and set as `FIREBASE_SERVICE_ACCOUNT_JSON` in Vercel (Production) for `send.ts`'s server-side Admin SDK calls.

**Verified**: `tsc --noEmit`, eslint, `npx vitest run` (217/217, unchanged — no new unit tests, this is browser/native-API wiring in the same style as the untested parts of `subscribe.ts`/`health-connect-client.ts`), and `npm run build` all clean. Migration `0095` applied by Carl, confirmed live via a direct `node --env-file=.env.local` query rather than trust — `push_device_tokens` existed, empty, right after.

**Even with all of the above, registration still silently did nothing on device — two further real bugs, found live, not guessed.** First: `AndroidManifest.xml` never declared `POST_NOTIFICATIONS` — on Android 13+ (this app targets SDK 36), an app that hasn't declared it gets no notifications toggle in system Settings at all, and `PushNotifications.requestPermissions()` can't show the runtime prompt either, indistinguishable from silent denial. Added it, plus `com.google.firebase.messaging.default_notification_icon` meta-data (without it, FCM's own SDK resolves the small-icon resource to 0 when auto-building a system notification for a backgrounded app — a known crash on receipt, not just a missing icon) — deliberately did **not** add a `default_notification_channel_id` override, since nothing in this app calls `createNotificationChannel()` and pointing at a channel that doesn't exist would silently drop every notification on Android 8+.

**Second, much bigger bug: `isNativePushSupported()` returned `false` on the real native app, every single time, confirmed via a temporary on-page debug line** (`bookings-view.tsx`, removed once resolved) showing `isNative=false` no matter how long the app had been open or how much it had been navigated around — ruling out a hydration timing race. Root cause, found via `curl` against the live domain rather than guessed: `myfitpod.app` (apex) 308-redirects to `www.myfitpod.app` at the Vercel level, but `capacitor.config.ts`'s `server.url` was set to the apex domain. Capacitor's native bridge (`Bridge.java`'s `WebViewLocalServer`) only injects `window.Capacitor` into pages matching its exact configured authority — once the WebView followed that redirect, it landed on a domain outside that scope, so the bridge (and therefore every Capacitor plugin — push, Health Connect, all of it) never existed on any page load, ever, since this app went native. Fixed by pointing `server.url` at `https://www.myfitpod.app` directly, skipping the redirect hop.

**A real secondary bug found and fixed in the same investigation**: this app's CSP (`proxy.ts`) is strict nonce-based (`script-src 'self' 'nonce-...' 'strict-dynamic'`, no `unsafe-inline` fallback) — but Capacitor's injected bridge `<script>` tag carries no nonce at all (it can't know this app's per-request nonce), so even once the domain was fixed, that script would have been silently blocked by CSP with zero console warning. Fixed via a WebView User-Agent check (`isCapacitorWebView()`, detects Android's own `"; wv)"` marker) that drops the nonce/`strict-dynamic` requirement to a plain `unsafe-inline` **only** for requests that already look like the native shell — real browser/PWA visitors keep the full strict policy untouched. This was a real permission-required edit — the harness's own safety classifier flagged relaxing a CSP as needing explicit sign-off before it would let the file be written, which Carl gave.

**Third bug, found after the above two were fixed and `isNative` finally read `true`: registration still silently never ran.** `/api/push/subscription-status` returned one combined `subscribed` boolean (`webPush.count > 0 || nativePush.count > 0`) — member 150 already had two old rows in `push_subscriptions` from earlier browser testing, so the native app's own auto-resubscribe effect read "already subscribed" and returned before ever calling `subscribeToNativePush()`, no error, nothing visible. Split the route into separate `webSubscribed`/`nativeSubscribed` flags; `bookings-view.tsx` now checks whichever one actually applies to the current platform.

**Delivery verified for real, not assumed from a 200 response**: a temporary self-service `/api/push/test-send` route (signed-in member only, always targets whoever calls it, no admin bypass — removed once done) sent a real push through the exact `sendPush()` path the waitlist trigger uses. Server reported `sentCount: 3` (the native token plus two old web-push rows) with no errors — but nothing appeared on the phone at first. Turned out to be delivery delay, not a bug — it landed a short while later, confirmed by Carl watching it arrive.

**Also found and fixed in the same stretch**: `booking-grid.tsx`'s own profile-link icon on `/book` shared the exact top-right corner Pod Assist's bubble is pinned to (the only page where that's true — every other page with the bubble relies on a bottom nav for `/profile` instead) — first repositioned, then removed outright once Carl pointed out `<BottomNav />` (already rendered on that page) has its own Profile tab, making the separate icon redundant on top of broken.

**Two genuine mistakes on my own part this session, both self-caught before Carl hit them**: an XML comment containing a literal `--` (invalid — XML comments can't contain `--` except at the closing `-->`) broke `AndroidManifest.xml` parsing twice, from two separate edits, since the existing file's own convention uses a real em dash and I used a plain double-hyphen instead both times. And a JDK-toolchain-resolver fix (below) that was built and verified but never actually committed until the very end of the session, caught only during final cleanup.

## Health Connect permission trim + full Play Store submission — 2026-09-09, same session

**`@capgo/capacitor-health`'s own bundled manifest declares 46 Health Connect read/write permissions unconditionally** — `health-connect-client.ts` only ever reads 4 (steps, sleep, restingHeartRate, HRV) and this app never writes to Health Connect at all. Found via Play Console's Health apps declaration, which requires a separate written justification per declared permission — ~40 fields for things never used, and Google's own guidance says unused ones should be removed, not justified. `tools:node="remove"` in `AndroidManifest.xml` strips the 42 unused ones at manifest-merge time (verified against the actual merged output, not assumed) rather than editing the plugin's own manifest, which npm would overwrite on the next install.

**Every CLI-verified native change this session** (JDK toolchain, manifest fixes, permission trim) **was built and confirmed via a clean `gradlew bundleRelease` run before asking Carl to touch Android Studio again** — given how many rebuild rounds this session already cost him, each one was checked first rather than sent on faith. `versionCode` climbed 2→6 across the session (permission fix, icon meta-data, local-notifications, domain fix, Health Connect trim, first Production release).

**Full Play Store submission completed this session, not just prepped**: dedicated review test account created (`playstore-review@myfitpod.app`, Hove, fully onboarded — waiver signed, privacy policy accepted, tour skipped, trial extended a year so `hasPremium()` grants access with no membership row needed, 5 credits granted) via a disposable Admin-API script (`scripts/create-play-review-account.mjs`). New public `/delete-account` page + `/api/account/delete-request` (IP-rate-limited, forwards to staff via existing `getStaffRecipients` routing, deliberately manual not automated — a real person checks Stripe/booking history before anything's deleted) satisfies Play's account-deletion requirement, which this app had no mechanism for at all before tonight. Content rating (All Other App Types, In-App Purchases flagged, ratings 3+/PEGI 3/Everyone across regions), target audience (18+, minors restricted), Data Safety questionnaire (full pass — location, personal info, financial info, health/fitness, messages, device IDs, each with collected/shared/ephemeral/required/why-collected answered against the real code, not guessed), financial features (none apply), app category (Health & Fitness), store listing copy, app icon (existing `icon-512.png`), feature graphic (Carl's own Canva design), and phone screenshots all completed. **Submitted for review** via Production track (`versionCode 6`) — sitting in Google's automated pre-check as of session end, not yet approved.
